# Semantic judgment predicates and pluggable backends

**Status:** implemented on `feat/judgment-primitives`. The design below matches
the shipped surface, not an aspiration.

## 1. Overview

DML models semantic decisions with ordinary Prolog. Alongside the generative
primitives (`task/N`, `prompt/N`, `llm/2`) and the host tool bridge (`exec/2`),
the SDK now provides **judgment predicates**: bounded, typed questions answered
against an explicit state.

A judgment is one of three generic kinds:

| Kind | Answers | DML value |
| --- | --- | --- |
| `choose` | one of a closed set of options | the option atom |
| `rate` | one of an ordered list of levels | the level atom |
| `verify` | a yes/no proposition | `yes` \| `no` \| `unknown` |
| `probability` | a yes/no proposition | a number in `[0, 1]` |

Judgments are implemented by swappable `JudgeBackend`s. The SDK ships three:

- `llm` — an ordinary LLM (pi's active model when injected, otherwise the SDK
  provider path).
- `jev` — TypeSafe System One, giving calibrated probabilities and confidence.
- `mock` — deterministic answers for tests and for developing the Jev path
  without an API key.

The DML surface is the same regardless of backend:

```prolog
judge(Message, [
    choose("Which team should handle this?",
           [billing-"Charges and refunds", orders-"Delivery", account-"Login"]) - Team,
    rate("How frustrated is the customer?", [calm, frustrated, angry]) - Frustration,
    verify("Does the message ask for a refund?") - Refund,
    probability("Is this urgent?") - Urgency
]),
(   Refund == yes, Team == billing
->  answer("Escalating to the refund queue.")
;   format(string(R), "route=~w frustration=~w urgency=~w", [Team, Frustration, Urgency]),
    answer(R)
).
```

## 2. Design principles

1. **Concept before implementation.** The language defines `choose`, `rate`,
   `verify`, and `probability`. Jev and LLMs are backends, not syntax.
2. **Explicit state, no memory.** Judgments never read or write `system/1`,
   `user/1`, or prior `task/N` memory. They are functions of an explicit state,
   which makes them backtrack-safe and reproducible.
3. **Bounded answers.** A `choose` answer is always one of the supplied options;
   a `rate` answer is always one of the supplied levels.
4. **Honest provenance.** Every backend declares capabilities. A skill that
   needs calibrated probabilities can require them and fail clearly otherwise.
5. **Memoize, never re-sample.** A judgment is cached per run by backend, model,
   state, and questions, so backtracking reuses the answer.
6. **DML owns policy.** Thresholds, weights, search, and side effects stay in
   Prolog. Backends produce evidence.
7. **Jev is evidence, never authorization.** Irreversible actions keep hard
   gates and approvals.

## 3. Public API

Types live in `src/judge/types.ts` and are re-exported from the package root.

```ts
type JudgeQuestionKind = 'choose' | 'rate' | 'verify' | 'probability';

type JudgeBasis =
  | 'calibrated' | 'self_reported' | 'estimated'
  | 'label' | 'human' | 'mock';

interface JudgeQuestion {
  id: string;                       // generated by the bridge
  kind: JudgeQuestionKind;
  instruction: string | JsonValue;
  options?: JudgeOption[];          // choose
  levels?: JudgeLevel[];            // rate
  criteria?: { true?: JsonValue; false?: JsonValue };  // verify
}

interface JudgeAnswer {
  id: string;
  kind: JudgeQuestionKind;
  value?: string;                   // option | level | yes/no/unknown
  probability?: number;             // verify / probability
  confidence?: number;              // choose / rate
  distribution?: number[];          // aligned to options or levels
  basis: JudgeBasis;
}

interface JudgeCapabilities {
  calibrated: boolean;
  probability: boolean;
  confidence: boolean;
  independentQuestions: boolean;
  batch: boolean;
  structuredCriteria: boolean;
  maxQuestions: number;
  maxOptions: number;
  maxLevels: number;
  stateTokenBudget: number;
}

interface JudgeBackend {
  readonly id: string;
  readonly capabilities: JudgeCapabilities;
  complete(request: JudgeBackendRequest): Promise<JudgeBackendResponse>;
}
```

Factories:

```ts
createLLMJudgeBackend(options?: LLMJudgeBackendOptions): JudgeBackend;
createJevJudgeBackend(options: JevJudgeBackendOptions): JudgeBackend;
createMockJudgeBackend(options?: MockJudgeBackendOptions): JudgeBackend;
createMockJevJudgeBackend(options?: MockJudgeBackendOptions): JudgeBackend;
```

SDK options and methods:

```ts
createDeepClause({
  // ...
  judgeBackend?: JudgeBackend,                  // a default backend
  judgeBackends?: Record<string, JudgeBackend>, // named registry
  defaultJudge?: string,                        // default name
});

runDML(code, { judgeBackend?: string /* per-run default override */ });

sdk.registerJudgeBackend(name, backend);
sdk.setJudgeBackend(name);
sdk.getJudgeBackends();
sdk.getJudgeCapabilities(name?);
```

If no judge backend is supplied, the SDK creates an `llm` judge backend from the
same model options, so the predicates work out of the box.

## 4. DML surface

### 4.1 `judge(+State, +Specs)`

Each element of `Specs` is `Question - Output`. All questions are sent in one
request and the output variables are bound when it completes.

Question grammar:

```prolog
choose(Instruction, Options)            % Option | Option-"description"
rate(Instruction, Levels)               % Description | level(Description, Examples)
verify(Instruction)
verify(Instruction, criteria(True, False))
probability(Instruction)
```

### 4.2 One-off predicates

```prolog
choose(State, Question, Options, Choice)
rate(State, Question, Levels, Level)
verify(State, Question, Truth)          % yes | no | unknown
probability(State, Question, P)         % number
holds(State, Question)                  % semidet: succeeds when verify == yes
holds(State, Question, Threshold)       % semidet: succeeds when probability >= Threshold
```

### 4.3 Scoping and capability gating

```prolog
with_judgment(Backend, Goal)
require_judgment(Capability, Goal)
```

`with_judgment/2` scopes a named backend for `Goal`. `require_judgment/2` records
a required capability; the runner rejects the next judgment request when the
active backend lacks it, so a calibration-dependent gate cannot silently run on
an uncalibrated backend. (`require_judgment/2` gates judgment requests; it does
not gate unrelated side effects that precede them.)

### 4.4 State marshalling

A state term maps to JSON as:

- a list whose elements are all `Key-Value` pairs -> a JSON object;
- any other list -> a JSON array (`arr([...])` forces an array);
- nested structures recursively;
- atoms, strings, numbers, `true`, `false`, `null` -> scalars.

## 5. Runtime

```
DML: judge(State, Specs)
  -> meta-interpreter split_specs/3 -> normalized questions + output vars
  -> engine_yield(request_judgment(payload{state, questions, backend, requires}))
Runner:
  -> resolve backend (spec > with_judgment > run override > default)
  -> check required capabilities
  -> cache lookup keyed by (backend.id, model, state, questions)
  -> backend.complete({ state, questions, signal, model })
  -> post_judgment_result(session, success, [Values])
Meta-interpreter:
  -> bind output vars in order
```

- **Request/response:** `request_judgment/1` on the way out;
  `post_judgment_result/3` and the `judgment_done` signal on the way back.
- **Events:** `task_activity` with `judgeBackend`, `judgeQuestionIds`, and
  `judgeState` (`started`/`completed`/`failed`); `usage` with `usageSource:
  'judge'` and `usageModel`.
- **Cancellation:** the backend receives the run `AbortSignal`; an abort fails
  the judgment and the Prolog goal (with a warning event).
- **Memoization:** per `run()` invocation. Repeated identical judgments (for
  example across backtracking) reuse the first answer.
- **Nested tools:** a judgment inside a `tool/2` body is handled inline, with
  events forwarded to the tool-call stream.
- **Gas:** each judgment request consumes one gas step.

## 6. Backends

| | `llm` | `jev` | `mock` / `mockJev` |
| --- | --- | --- | --- |
| calibrated | no | yes | no / yes |
| probability | yes (self-reported) | yes (calibrated) | yes |
| confidence | no | yes | yes |
| independent questions | no | yes | yes |
| batched request | yes (single prompt) | yes | yes |
| structured criteria | no | yes | yes |
| external key | pi's existing | `TYPESAFE_API_KEY` | none |

### `llm`

Builds one prompt from the state and the numbered questions, requests strict
JSON, validates every answer against the schema, and marks answers
`self_reported` (probability present) or `label`. Uses the injected `LLMBackend`
when present, otherwise the SDK provider path. It never uses DML memory or
tools.

### `jev`

Maps `choose`->`choice`, `rate`->`score`, `verify`/`probability`->`noul`,
calls `POST {baseUrl}/v1/systemone`, retries on `429`/`529` with backoff, honors
the abort signal, and forwards `input_tokens`/`output_tokens`. `rate` binds the
highest-probability level. Answers are `calibrated`. The API key is supplied by
the caller; the SDK never reads or stores credentials.

### `mock`

Deterministic, schema-valid answers with no network. `createMockJevJudgeBackend`
advertises Jev-like calibrated capabilities, so the Jev code path can be
developed and exercised before an API key exists.

## 7. Configuration and selection

Precedence for the backend used by a judgment:

1. `with_judgment/2` scope in the DML program;
2. `RunOptions.judgeBackend` for the run;
3. `CreateOptions.defaultJudge`;
4. the first registered backend.

Register named backends at construction or later:

```ts
const sdk = await createDeepClause({
  model,
  llmBackend,
  judgeBackends: {
    llm: createLLMJudgeBackend({ llmBackend }),
    jev: createJevJudgeBackend({ apiKey: process.env.TYPESAFE_API_KEY }),
    mock: createMockJevJudgeBackend(),
  },
  defaultJudge: 'llm',
});
```

Enable real Jev once a key is available by providing the `jev` backend and
selecting it (`defaultJudge: 'jev'` or `/dc-run --judge=jev` in the pi
extension). No DML source changes are needed.

## 8. Testing

`tests/judge.test.ts` covers the DML surface end to end with mocks: batch and
one-off predicates, judge events, memoization, capability gating,
`with_judgment/2`, and SDK introspection.

`tests/jev-backend.test.ts` covers the real Jev mapping with a fake `fetch`:
request shape and auth, answer mapping (choice/score/noul), usage attribution,
`429` retry, and the missing-key failure. This means the Jev path is fully
tested before an API key is obtained; only the live HTTP round trip is pending.

## 9. Current limitations

- The DML surface binds primary values only. `confidence` and `distribution`
  are carried on backend answers and in events but are not exposed as DML terms
  yet.
- `verify` derives `yes`/`no` at a 0.5 default; use `probability` when a custom
  threshold is needed.
- `require_judgment/2` is enforced at the next judgment request, not before
  arbitrary side effects.
- The `llm` backend's confidence is not calibrated and is marked as
  `self_reported`/`label`.
- `rate` on the Jev backend returns the argmax level; the weighted `score` and
  distribution remain available on the backend answer.

## 10. Using this from `deepclause-pi`

The extension will only need to construct and select backends:

```ts
const judgeBackends: Record<string, JudgeBackend> = {
  llm: createLLMJudgeBackend({ llmBackend: piBackend }),
};
if (config.judgment.jev.enabled && process.env[config.judgment.jev.apiKeyEnv]) {
  judgeBackends.jev = createJevJudgeBackend({
    apiKey: process.env[config.judgment.jev.apiKeyEnv],
    model: config.judgment.jev.model,
  });
}
const sdk = await createDeepClause({
  model: model.id,
  llmBackend: piBackend,
  judgeBackends,
  defaultJudge: config.judgment.default,
});
```

`/dc-run --judge=jev` maps to `RunOptions.judgeBackend`; `/dc` reports
`getJudgeBackends()` and `getJudgeCapabilities()`. The `llm` backend keeps pi's
"use my active model and credentials" principle, and Jev remains opt-in.
